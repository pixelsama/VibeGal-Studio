## 2. 产品背景

VibeGal-Studio 是图优先、数据驱动的 Galgame 项目编辑器和实时预览器。创作者在故事图中组织
节点、分支和结局，通过节点指令改变故事状态，运行时依据状态决定自动分流。

项目同时强调两类使用者：

- 人类创作者应面对低门槛、符合叙事思维的界面；
- 外部 Agent 可以直接操作 JSON、schema、CLI 和技术标识。

两者不应使用同一套界面语言。`system.playthroughCount`、`number`、表达式源码等内容可以继续
作为项目文件和外部 Agent 的稳定接口，但不应无条件暴露给普通创作者。

产品边界仍然是「无内置 AI」：本议题不涉及应用内 AI、聊天框或模型集成。

## 3. 现有改动与当前问题

### 3.1 Spec 24 已做的事情

当前工作区正在实施
[Spec 24 — Story State Authoring](./24-story-state-authoring.spec.md)，主要包括：

- 将作者侧的「变量」改称「故事状态」；
- 增加 `flag`、`meter`、`state`、`counter`、`text` 等创作用途；
- 数值范围、分段名称和状态枚举；
- 句子化条件编辑器；
- 「如果……否则」式分流规则；
- 「增加／减少／设为」式状态改变编辑器；
- `chose.*`、`seen.*` 剧情经历和 `system.*` 系统状态；
- 安全重命名和运行时数值钳制；
- 一套状态试算控件。

这些功能解决了一部分表单和词汇问题，但用户实际运行后仍然几乎感受不到产品层面的变化。

### 3.2 「故事状态」入口仍然过深

目前入口依然是：

```text
脚本 → 右侧 Inspector → 分析 → 向下滚动 → 故事状态
```

相关代码：

- `packages/studio/src/features/script/ScriptWorkspace.tsx`
- `packages/studio/src/features/script/GraphAnalysisPanel.tsx`
- `packages/studio/src/features/script/StoryStatePanel.tsx`

这意味着故事状态仍被当作一种「分析结果」，而不是核心创作对象。即使内部组件改写很多，
应用的整体信息架构和旧版本相比也没有明显改变。

### 3.3 默认项目几乎展示不出新功能

默认/示例图只有简单线性连接、没有登记的故事状态，也没有自动分流。因此以下界面都不会自然出现：

- 多出口节点的分流方式；
- 句子化条件；
- 好感度、旗标、枚举状态卡；
- 状态改变指令；
- 分流试算结果。

需要评审「普通空白项目的空态教学」和「独立教程/示例项目」应如何分工。不要未经判断就把大量
虚构状态写进每个新项目，避免用户新建项目后首先要删除示例数据。

## 4. 预览页面的可见失败

当前预览采用：

```text
预览舞台 + 右侧常驻“运行状态”侧栏
```

侧栏固定占用约 260–320px，列出：

- 当前节点；
- 背景、说话人、选项、背景音乐、语音、角色立绘；
- 本轮、跨周目、未登记、系统变量；
- 可直接编辑的变量控件；
- 重置变量按钮。

相关代码：

- `packages/studio/src/features/preview/Preview.tsx`
- `packages/studio/src/features/preview/RuntimeStateInspector.tsx`
- `packages/studio/src/features/script/StateTrial.tsx`

用户截图中的典型失败是系统状态区域：

```text
变量
系统状态
通关次数
▼ 技术详情
system.playthroughCount · number · 运行时提供
[ 0 ]

上次达成的结局
▼ 技术详情
system.lastEndingId · null · 运行时提供
[     ]

[重置变量]
```

主要问题不只是样式：

1. 狭窄侧栏里堆叠「变量／系统状态／状态名／技术详情」多层标题，信息密度与字号不匹配。
2. 长内部标识被强制断行，例如 `playthroughCo / unt`。
3. 只读系统事实使用输入框形态，暗示用户可以或应该编辑。
4. `number`、`null`、`运行时提供` 是实现信息，无法帮助作者完成创作任务。
5. 大量字段持续显示「无」，占据空间但缺少决策价值。
6. 「重置变量」没有说明重置的是调试会话、存档、项目默认值还是故事内容。
7. 预览舞台是主要对象，却被默认常驻的调试器压缩。

仅缩小字体、调整间距或翻译 `number` 不足以解决这些问题。

## 5. 当前交互还混合了两种不同任务

现在预览页存在两套状态修改机制：

1. 舞台上方的「试算」：设置点击「从这里试玩」时使用的初始假设；
2. 右侧运行状态输入框：直接修改已经运行起来的调试会话。

界面没有清楚解释它们的生效时机、持续时间和是否会修改项目。创作者容易产生以下疑问：

- 改完值会立刻影响当前剧情，还是要重新开始试演？
- 这是临时假设，还是修改故事开始时的值？
- 为什么项目中的实际状态改变指令没有变化？
- 「重置变量」会不会破坏项目或存档？

这两种任务可能应该拆开：

- **试演前情**：开始前声明「假设此前发生了什么」，只影响本次试演；
- **剧情检查**：运行中只读解释「为什么现在是这个值、为什么走到这里」。

请评审者判断这种拆分是否正确，以及是否存在更低门槛的统一方式。

## 6. 用户提出的核心产品假设

以下是用户当前倾向，仍需独立评审。

### 6.1 作者侧不出现「声明和初始化变量」

用户希望采用：

> 创建一个故事状态后，它从游戏开始就已经存在。剧情中只有改变状态，没有临时声明状态。

例如创建「雪的好感度」时，作者回答：

- 要记录什么；
- 故事开始时是多少；
- 允许变化的范围；
- 新游戏时重新开始，还是跨周目保留。

之后节点里只提供符合用途的动作：

- 是否发生：标记为已发生／恢复为未发生；
- 数值：增加、减少、调整为；
- 状态：切换为；
- 次数：增加一次或调整为；
- 文本：改成。

内部数据契约仍可保留 `VariableDeclaration`、`type`、`default`、`scope`。问题是这些概念是否应
从创作者界面完全隐藏，以及 `null`/未设置状态是否还有真实创作价值。

请特别评审：

- 所有状态都在新游戏开始时拥有确定值，是否足以覆盖目标 Galgame 场景？
- 「尚未发生」是否应表示为 `false`，而不是未初始化？
- 文本或上次结局这类「尚无」是否需要 `null`，如果需要应如何用作者语言呈现？
- 删除、重命名、跨周目状态与旧项目兼容怎样处理？

### 6.2 故事状态必须有单独查看和管理页面

用户不接受故事状态继续藏在分析侧栏中。一个候选信息架构是：

```text
故事 / 脚本工作台

[剧情流程] [故事状态] [需要处理]
```

候选职责：

- **剧情流程**：节点图、章节、分流规则；
- **故事状态**：创建、查看、修改状态定义和初始状态，并显示使用位置；
- **需要处理**：结构问题、错误条件、不可达结局、未登记状态等。

这只是候选方案。请评审：

- 「故事状态」应作为脚本内部一级入口，还是应用顶栏独立工作区？
- 「分析」是否应被重构为「需要处理」，还是保留覆盖率等高级视图？
- 状态详情应该是完整页面、主从布局、抽屉还是 Inspector？
- 如何让作者从状态卡快速前往「哪里改变它／哪里判断它」？
- 如何让作者从节点指令或分流规则快速返回状态详情？

### 6.3 预览中的状态检查应只读并可导航

用户倾向于：预览调试不能继续模仿程序员的变量监视器。

候选原则：

- 默认预览不显示状态侧栏；
- 用户主动开启「剧情检查」后才显示；
- 检查面板不允许直接修改当前运行值；
- 面板解释状态从哪里来、在哪里改变、为什么触发当前分支；
- 提供跳转到故事状态详情、状态改变指令或分流规则的入口；
- 真正的修改发生在故事创作位置，而不是预览内存里。

候选内容：

```text
剧情检查

当前位置
天台告白

发生过的状态变化
雪 · 好感度    65（喜欢）
最近在「雨夜交谈」增加了 10
[查看这次变化] [查看全部变化]

拿到钥匙       已发生
在「旧校舍」被标记为已发生
[前往该节点]

下一处分流
✓ 拿到钥匙
✓ 雪 · 好感度达到“喜欢”
因此会进入「雪线结局」
[查看分流规则]
```

请评审这种面板是否应该：

- 作为右侧可开关面板、底部抽屉或独立检查模式；
- 只列变化过和当前分流相关的状态，还是提供完整列表；
- 显示当前值、变化来源、条件解释中的哪些组合；
- 在场景快照模式中完全隐藏，或提供面向渲染层作者的另一种「场景数据」入口。

## 7. 需要重点判断的技术可行性

### 7.1 “跳到状态改变位置”需要怎样的导航

静态项目分析已经可以找到：

- 哪些节点的 `set` 指令写入某个状态；
- 哪些 auto edge 条件读取某个状态。

但要从预览精确跳转到「本次运行中最近一次改变它的指令」，可能还需要：

- 运行时记录状态写入事件；
- 事件包含节点 ID、稳定指令 ID、旧值、新值、改变方式；
- 回滚、读档、跨周目状态和调试试演时保持一致；
- 导航能够从预览切到脚本工作区、打开节点并聚焦具体指令；
- 分流解释能够聚焦具体 edge。

请检查现有 `DecisionLogEvent`、稳定指令 ID 和导航模型能复用多少，是否需要新的运行时 trace，
以及 trace 应只存在内存还是进入存档。

相关入口：

- `packages/engine/src/graphPlayer.ts`
- `packages/engine/src/runtimeContract.ts`
- `packages/studio/src/features/preview/useProjectPlayer.ts`
- `packages/studio/src/features/script/ScriptWorkspace.tsx`
- `packages/studio/src/lib/navigation.ts`

### 7.2 “为什么走这条分支”需要怎样的解释模型

现有引擎能计算条件真假，但创作者式解释可能需要：

- 将表达式还原为句子；
- 展示每个子条件的实际值与是否满足；
- 标识最终胜出的 edge；
- 区分「当前值下不满足」和「结构上永远走不到」；
- 对高级表达式提供安全降级，而不是显示错误的半解释。

请判断现有 `storyState.ts`、`ConditionEditor.tsx` 和 `BranchRules.tsx` 是否足以复用，哪些能力应
下沉到共享领域模型，避免预览和脚本各自实现一套解释器。

### 7.3 系统状态与剧情经历

当前运行时存在：

- `system.playthroughCount`
- `system.lastEndingId`
- `chose.<edgeId>`
- `seen.<nodeId>`

请评审创作者 UI 应如何分类：

- 系统自动记录的游戏进度；
- 作者创建的故事状态；
- 由玩家路径自动推导的剧情经历。

不要默认把所有 `seen.* = false` 或全部内部 ID 铺在面板里。需要提出信息筛选原则和用户语言。

## 8. 评审时应避免的局部修补

以下改法不能单独作为最终建议：

- 只把字号调小；
- 只给右侧栏加卡片和间距；
- 只把 `number` 翻译成「数值」；
- 只隐藏「技术详情」但保留常驻变量监视器；
- 继续在预览里直接编辑运行时值，只更换按钮文案；
- 只给默认项目塞几个示例变量，却不解决核心入口；
- 为创作者新增另一套与现有试算并存的第三套状态修改入口。

评审应优先解决任务模型与信息架构，再讨论视觉样式。

## 9. 希望接手 Agent 输出的格式

建议以以下结构交付：

### A. 结论摘要

- 哪些问题判断成立；
- 哪些用户假设应接受、修改或拒绝；
- 推荐的总体产品模型。

### B. 推荐信息架构

- 应用级和脚本工作台级入口；
- 故事状态页面结构；
- 预览、试演、剧情检查之间的关系；
- 从检查结果返回编辑位置的导航闭环。

### C. 关键交互示意

至少给出以下低保真结构：

- 故事状态列表和详情；
- 从这里试演；
- 只读剧情检查；
- 当前分流解释。

### D. 状态生命周期与词汇

- 作者创建状态时回答什么；
- 游戏开始时如何存在；
- 节点里如何改变；
- 系统状态、剧情经历、跨周目状态如何呈现；
- 哪些技术字段完全隐藏，哪些放入高级详情。

### E. 技术影响

- 可复用的现有代码；
- 需要新增或调整的数据模型；
- 是否需要运行时状态变化 trace；
- 导航和稳定指令定位；
- 兼容性与迁移风险。

### F. 分期建议

请区分：

- 第一阶段必须修复的信息架构问题；
- 第二阶段的因果解释与跳转；
- 第三阶段的教程、示例和高级调试能力。

### G. 待用户确认的决策

只列真正会改变产品方向的问题，并为每项给出推荐选项与取舍。
